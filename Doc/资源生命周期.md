# 目标

修复多线程渲染下的资源生命周期问题：

```
MainThread 生成 GfxCommand
        ↓
RenderThread 消费 CommandGroup
        ↓
JobThread 录制 D3D12 CommandList
        ↓
ExecuteCommandLists
        ↓
GPU 执行
```

当前资源的 fence 只会在 JobThread 实际录制并提交 CommandList 后写入。

因此存在空窗：

```
MainThread 已提交 GfxCommand
        ↓
资源失去外部引用并析构
        ↓
JobThread 尚未开始录制
        ↓
GfxCommand 中的裸指针 UAF
```

不要使用“100 帧后再销毁”这种经验性延迟方案。

采用：

> **CommandGroup 保证 CPU 异步阶段生命周期，Fence 保证 GPU 执行阶段生命周期。**

# 设计

资源生命周期拆为两段：

```
CPU Lifetime                         GPU Lifetime

CommandBuffer
    ↓
CommandGroup
    ↓
Record Job
    ↓
ExecuteCommandLists
    |------------------------------------>
    |                                    |
Strong Ref                          Fence Tracking
```

## CPU 阶段

`CommandGroup` 持有该批命令可能访问的对象的强引用。

`GfxCommand` 继续使用裸指针，不修改 hot path 数据结构。

例如：

```
struct CommandGroup
{
    Vector<GfxCommand*> _cmds;
    Vector<Ref<Object>> _keep_alive_objects;
    SubmitParams _params;
    u32 _submission_index = 0u;
};
```

只要：

```
CommandGroup / Record Job
```

仍然存在，对应资源和对象就不会析构。

# CommandBuffer 修改

在 `CommandBuffer::Impl` 中加入：

```
Vector<Ref<Object>> _keep_alive_objects;
HashSet<Object*> _keep_alive_set;
```

增加内部函数：

```
void KeepAlive(Object* object);
```

语义：

```
void CommandBuffer::KeepAlive(Object* object)
{
    if (object == nullptr)
        return;

    if (_impl->_keep_alive_set.insert(object).second)
        _impl->_keep_alive_objects.emplace_back(object->SharedFromThis());
}
```

具体 `Ref` 获取方式根据 AiluEngine 当前 Object/Ref 实现调整，不要额外实现新的引用系统。

保证同一个对象在一个 CommandBuffer 中只持有一次强引用。

# 哪些对象需要 KeepAlive

原则：

> **任何 GfxCommand 在 RenderThread / JobThread 中可能解引用的对象，都必须 KeepAlive。**

至少检查：

```
VertexBuffer
IndexBuffer
ConstantBuffer
GPUBuffer
Texture
RenderTexture
Material
Mesh
Shader
ComputeShader
RayTracingShader
RayTracingScene
RayTracingGeometry
GpuResource
```

重点检查这些接口：

```
DrawIndexed
DrawInstanced
DrawIndexedInstanced
DrawMesh
DrawMeshIndirect
DrawProceduralIndirect

SetRenderTarget
SetRenderTargets

SetGlobalTexture
SetGlobalBuffer

Blit

Dispatch
DispatchRays

BuildAS

StateTransition
ResourceBarrier
InsertUAVBarrier

ReadbackBuffer
```

例如：

```
void CommandBuffer::StateTransition(GpuResource* resource, EResourceState state, u32 sub_res)
{
    KeepAlive(resource);

    // 原有 GfxCommand 创建逻辑
}
```

对于：

```
DrawIndexed(vb, ib, cb, material);
```

至少：

```
KeepAlive(vb);
KeepAlive(ib);
KeepAlive(cb);
KeepAlive(material);
```

# 间接依赖处理

不要在主线程递归抓取：

```
Material -> Texture
Material -> Shader
Mesh -> VertexBuffer
```

除非 GfxCommand 中直接保存并在 JobThread 解引用这些子对象。

优先遵循：

> **谁被 GfxCommand 保存为指针，谁 KeepAlive。**

如果 `ProcessGpuCommand()` 在执行期间通过 `Material*` 动态查询 Texture/Shader，则保持 `Material` 活着仍然不一定保证内部 Texture 活着。

遇到这种情况优先让对应拥有者自身正确持有：

```
Material
 ├─ Ref<Shader>
 ├─ Ref<Texture>
 └─ Ref<GPUBuffer>
```

不要让 `CommandBuffer` 承担完整资源依赖图。

# 提交阶段

当前：

```
Vector<GfxCommand*> CommandBuffer::TakeCommands();
```

增加：

```
Vector<Ref<Object>> TakeKeepAliveObjects();
```

或者直接返回一个统一结构：

```
struct RecordedCommands
{
    Vector<GfxCommand*> _commands;
    Vector<Ref<Object>> _keep_alive_objects;
};
```

推荐尽量减少现有接口修改，可以继续分别 Take。

`GpuCommandWorker::Push()` 构造 `CommandGroup` 时：

```
CommandGroup(
    std::move(commands),
    std::move(keep_alive_objects),
    std::move(params),
    submission_index);
```

# Job 生命周期

AiluEngine 当前已经使用：

```
Ref<CommandGroup>
```

捕获到 Record Job 中。

保持这一机制。

因此：

```
Record Job
   ↓ owns
CommandGroup
   ↓ owns
_keep_alive_objects
   ↓ owns
Resource/Object
```

Job 完成前，资源天然不会析构。

无需新增：

```
pending_use_count
cpu_fence
recording_ref_count
100-frame grace period
```

# GPU 阶段

保留当前：

```
D3DCommandBuffer::_used_resources
```

以及：

```
MarkUsedResource()
```

和：

```
void D3DCommandBuffer::PostExecute()
{
    for (auto& resource : _used_resources)
        resource->Track(_fence_value);
}
```

不要用 CPU KeepAlive 替代 fence tracking。

两者职责不同：

```
_keep_alive_objects
    ↓
保证 CPU 尚未完成录制/提交时对象存在

_used_resources + fence
    ↓
保证 GPU 尚未完成执行时 native resource 不被释放
```

# 推荐补充：Deferred GPU Release

如果当前：

```
GpuResource::~GpuResource()
```

会直接销毁：

```
ID3D12Resource
Descriptor
其他 GPU native object
```

建议补一个简单：

```
DeferredReleaseQueue
```

但这可以作为第二阶段完成，不阻塞本次 CPU UAF 修复。

结构：

```
struct DeferredReleaseItem
{
    u64 _fence_value = 0u;
    ComPtr<ID3D12Resource> _resource;
};
```

只有：

```
completed_fence >= _fence_value
```

后才真正释放 native resource。

如果 AiluEngine 当前已有可靠的 fence 延迟销毁机制，则直接复用，不重复实现。

# CommandBuffer::Clear

必须同时清空：

```
_keep_alive_objects.clear();
_keep_alive_set.clear();
```

注意只允许在 CommandBuffer 内容已经：

```
Take
或
完全废弃
```

后执行。

不能在 CommandGroup 已经拿到命令，但 ownership 尚未转移时提前 Clear。

# Debug 检查

Debug 构建增加辅助检查。

## 1. CommandGroup 生命周期

可记录：

```
CommandGroup name
submission_index
keep_alive object count
```

确认 Record Job 完成前没有提前析构。

## 2. GpuResource 析构

资源析构时，如果：

```
IsReferenceByGpu()
```

仍为 true，Debug 下报警：

```
AL_ASSERT(!IsReferenceByGpu());
```

如果当前析构设计允许把 native resource 转入 DeferredReleaseQueue，则不要 Assert object 本身，而检查 native resource 是否安全转移。

## 3. GfxCommand 裸指针检查

检查所有：

```
struct XXXCommand
```

中的：

```
Object*
GpuResource*
Material*
Mesh*
Shader*
```

确保对应 `CommandBuffer` API 调用时执行了 `KeepAlive()`。

# 性能要求

不要：

```
每个 DrawCommand 保存 Ref<>
每次 Bind 做 atomic ref count
每个资源维护 100 帧历史
```

推荐：

```
GfxCommand
    raw pointer

CommandBuffer / CommandGroup
    unique object strong refs
```

例如 1000 个 Draw 使用相同纹理：

```
1000 × Texture*
1 × Ref<Texture>
```

保持渲染 hot path 足够轻量。

# 实施顺序

1. 给 `CommandBuffer::Impl` 添加 KeepAlive 集合。
2. 实现 `KeepAlive(Object*)`。
3. 实现 `TakeKeepAliveObjects()`。
4. 给 `CommandGroup` 添加 `_keep_alive_objects`。
5. 提交 CommandBuffer 时将 ownership move 到 CommandGroup。
6. 审查所有生成 `GfxCommand` 的 API，补充 `KeepAlive()`。
7. 保持 Job 对 `Ref<CommandGroup>` 的现有 ownership。
8. 保持 `MarkUsedResource + Track(fence)` 现有 GPU 生命周期逻辑。
9. 添加 Debug 生命周期检查。
10. 做多线程压力测试。

# 测试

必须覆盖以下情况。

### Case 1：提交后立即销毁

```
创建 Texture
录制 Draw
提交 CommandBuffer
主线程立即释放 Texture
```

期望：

```
Texture 在 Record Job 完成前不析构
无 UAF
正常渲染
```

### Case 2：Job 人为延迟

在 Record Job 开头人为：

```
Sleep(100);
```

主线程立即释放相关资源。

期望仍然正确。

这是本问题最重要的回归测试。

### Case 3：大量并行 CommandGroup

连续创建大量：

```
CommandGroup
Draw
Dispatch
Blit
```

同时频繁创建/销毁临时资源。

期望：

```
无崩溃
无随机 descriptor/resource corruption
```

### Case 4：GPU 延迟

人为制造较重 GPU workload。

确保：

```
CPU KeepAlive 已释放
但 GPU fence 未完成
```

时 GPU native resource 仍然存在。

### Case 5：CommandBuffer Pool

反复：

```
Get
Record
Submit
Release
Get
```

确认旧 `_keep_alive_objects` 不会残留，也不会提前清理下一批资源。

# 完成标准

实现完成后应满足：

- 主线程 Submit 后可以立即释放资源引用。
- RenderThread / JobThread 不会访问已经析构的对象。
- 不依赖固定帧数延迟销毁。
- GfxCommand 仍然可以使用裸指针。
- 每个 CommandGroup 对同一对象最多持有一个强引用。
- GPU 生命周期继续由真实 submission fence 管理。
- 不增加每 Draw 的引用计数操作。
- CommandBuffer Pool 不产生跨帧资源引用泄漏。
- graphics job 开关打开/关闭均正常工作。

最终生命周期应为：

```
MainThread Record
        |
        | Strong Ref
        v
CommandBuffer
        |
        | move
        v
CommandGroup
        |
        | Ref<CommandGroup>
        v
Record Job
        |
        v
ExecuteCommandLists
        |
        +------ CPU ownership ends
        |
        | Track(fence)
        v
GPU execution
        |
        v
Fence completed
        |
        v
Native Resource can release
```

核心约束：

> **CPU 尚未提交的异步命令靠 ownership 保活；已经提交给 GPU 的资源靠 fence 保活。**
